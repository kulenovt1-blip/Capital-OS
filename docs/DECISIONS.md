# Журнал решений

Формат: **вопрос → что выбрал → почему → как поменять.** Помеченное ⚠️ — решения, которые сильнее всего влияют на числа.

## Стек и инфраструктура

**D1. Стек.** → TypeScript strict, PWA полностью на клиенте, Vitest, Vite, IndexedDB — как в инструкции §2. → Возражений нет. → —

**D2. sql.js / fflate / idb / fast-check / Preact заменены своим кодом.** → Свои: inflate, ZIP-ридер, read-only SQLite-ридер, обёртка IndexedDB, генератор property-тестов; UI на vanilla TS. → npm-реестр был закрыт (см. BLOCKERS B1). Бонус: у движка ноль runtime-зависимостей, а SQLite-ридер — хороший кусок для портфолио. → SQLite спрятан за интерфейсом `SqliteDb` (`engine/import/sqlite.ts`): чтобы вернуть `sql.js`, достаточно адаптера на ~20 строк с тем же интерфейсом. `fast-check` можно добавить и переписать `tests/support/prop.ts` на него.

**D3. UI без фреймворка.** → Vanilla TS + маленький хелпер `h()` для DOM. → Инструкция разрешает vanilla, а Preact поставить было нельзя. Логика важнее интерфейса. → Если захочешь Preact, экраны изолированы в `app/screens/*`, переписываются по одному.

## Деньги и даты

**D4. Ставки — в базисных пунктах (целые).** → `rateBp: 1450` = 14,50% годовых. → Иначе ставка была бы float и протекла бы в расчёт процентов. → —

**D5. Округление.** → Одна функция `mulDiv` (BigInt внутри), банковское округление (half-even) до тиына. Округление «вверх до 100 ₸» — отдельная `ceilTo`. → Инструкция §2. → `engine/money.ts`.

**D6. Формат суммы.** → `30 285 ₸`, тиыны показываются только если они не нулевые: `30 285,50 ₸`. Разделитель тысяч — неразрывный пробел. → Привычно для KZT. → `formatKZT` в `engine/money.ts`.

**D7. Даты.** → Строки `YYYY-MM-DD`, арифметика через UTC. Добавление месяцев прижимает день к концу месяца (31.01 + 1 мес. = 28/29.02). → Детерминизм и отсутствие часовых поясов. → `engine/date.ts`.

## Импорт MoneyManager

**D8. ⚠️ Знак суммы операции.** → Сумма берётся по модулю, знак задаёт `type` (Income +, Expense −). Отрицательная сумма в файле даёт предупреждение. → В инструкции не сказано; это самый частый вариант. → `MM_SCHEMA` в `engine/import/mmbackup.ts`.

**D9. ⚠️ Счёт без строки в `account_balance`.** → Если расчётный баланс 0 — ок; иначе сверка по счёту провалена. → Строже нельзя (заблокировало бы импорт пустых архивных счетов), мягче — нарушило бы критерий «до тиына». → `reconcileAccounts` в `engine/ledger.ts`.

**D10. Удалённые сущности.** → Фильтруются `isRemoved = 1` у операций, переводов, счетов, категорий и связей. `NULL` в `isRemoved` считается 0 (колонка могла быть добавлена `ALTER TABLE` позже). → —

**D11. Архивные счета.** _(часть про `ignoreInBalance` заменена D58)_ → Участвуют в сверке и в капитале (деньги на них реальны). Исключение из анализа — только явный флаг `excluded` в настройках счёта. Флаг `ignoreInBalance` из MoneyManager выставляет `excluded = true` по умолчанию при первом импорте. → Инструкция §3.1: «пометить технические счета как исключённые». → Экран «Настройки → Счета».

**D12. Системные категории без названия.** → Имя выводится из `icon` (`icon:<имя иконки>`), пользователь может переименовать в настройках. → Инструкция §3.1. → `categoryLabels` в настройках.

## Классификация

**D13. Правила по умолчанию.** → Ровно те, что в инструкции §3.2 (Накопительный счёт, Накопление, Долг, Возвращают долг, Беру в долг, Возвращаю долг, Бонус, Размен, Рассрочка). Остальные категории — `UNCLASSIFIED`, пока ты их не разметишь на экране «Импорт». Список «семейных» тегов по умолчанию пустой. → «Не придумывай»: угадывать, что «Продукты» — это `E_base`, я не стал. → Разметка в UI сохраняется как правило; JSON правил редактируется в «Настройках».

**D14. Сопоставление правила с категорией.** → Сначала по `uid` категории, потом по названию (без учёта регистра и пробелов по краям). Правило может уточняться тегом, группой тегов (`family`) или подстрокой комментария; первое совпавшее уточнение выигрывает. → Названия переносимы между бэкапами, uid — однозначны. → `engine/classify.ts`.

**D15. Несовместимый класс.** → Если правило даёт расходной операции доходный класс (или наоборот), операция становится `UNCLASSIFIED` с причиной «конфликт правила». → Иначе один неверный пункт правил тихо исказил бы все отчёты. → —

## Капитал и обязательства

**D16. ⚠️ Долги: операции vs обязательства.** → Кредиторка считается по операциям (`F_borrowed − F_borrowed_back`). `Obligation` вида `debt` — для долгов, которых нет в MoneyManager. Если есть и то и другое, поднимается предупреждение о возможном двойном учёте. → Иначе один долг считался бы дважды. → `engine/ledger.ts`, `computeCapital`.

**D17. Семейные рассрочки в обязательствах.** → Входят в «Обязательства» (как в формуле §3.3), но в разбивке показаны отдельно: «свои» / «семейные». → Платишь их ты, значит, это твой отток. → —

**D18. Дебиторка может уйти в минус.** → Не обрезается до нуля: если долг выдан до начала данных, а возврат попал в данные, это видно в объяснении. → Принцип «никакой магии». → —

**D19. Сопоставление платежей с графиком рассрочки.** → Операция-кандидат (по тегу, категории или подстроке комментария) привязывается к ближайшему неоплаченному платежу графика в окне ±15 дней. Платёж вне окна всё равно уменьшает остаток и помечается «вне графика». Ручная привязка перекрывает автоматическую. → Банки двигают даты на выходные. → `matchWindowDays` в настройках.

**D20. Корректировки.** → Ручные корректировки не участвуют в сверке с `account_balance` (сверка проверяет именно импорт), но участвуют в капитале. Комментарий обязателен. → Иначе сверка всегда сходилась бы «подгонкой». → —

## Цели (этап 2)

**D21. Свободные деньги.** → `Σ по ликвидным счетам (баланс − назначено на этом счёте) − резерв под обязательства до следующего дохода`. → Формула §4.2 п.3 вычитала бы деньги, назначенные на заблокированном депозите, из ликвидных — это двойной штраф. → `freeMoney` в `engine/goals.ts`.

**D22. Следующий доход.** → Если расписание доходов не задано, горизонт = 30 дней, и это явно пишется в объяснении. → `settings.defaultIncomeHorizonDays`.

**D23. Назначение сверх баланса счёта.** → Запрещено (ошибка с объяснением). Если баланс упал из-за трат — предупреждение «назначено больше, чем есть» с вариантами «снять X с цели Y». Варианты отсортированы: сначала цели с меньшей важностью, при равенстве — по `id`. → Инвариант 1 §4.2, принцип «не урезать молча». → —

**D24. Назначение на родителя и на подцели.** → Разрешено и то и другое; одна запись `GoalFunding` всегда принадлежит ровно одной цели, а прогресс родителя = сумма подцелей + прямое назначение. Двойной учёт исключён структурно. → Инвариант 2 §4.2. → —

**D25. Отмена или завершение цели с деньгами.** → Нельзя, пока на ней есть назначенные деньги: система предлагает, куда их снять. «Цель достигнута» только предлагается, статус не меняется сам. → Принцип 6: ничего не менять молча. → —

**D26. Горизонт цели.** → По сроку (`deadline`, иначе `desiredDate`): до 3 мес. — small, до 12 — medium, до 36 — long, дальше или без срока — major. Можно переопределить. → Пороги в `settings.horizonMonths`. → —

**D27. Резерв.** → Цель с `role = safety`; цель по умолчанию — 3 медианных месяца `E_base` за 6 полных месяцев (`targetRule: months_of_base`). Медиана чётного числа месяцев = среднее двух средних с банковским округлением. → §12 инструкции. → `settings.reserveMonths`.

**D28. Стартовые цели из §4.3.** → Не создаются автоматически. На экране «Цели» есть кнопка «Создать пример из инструкции» — создаёт их с суммами `0 ₸` и пометкой `TODO: подтвердить`. → «Не придумывай финансовые данные». → —

## Капитал (добавлено при реализации, сессия 2)

**D29. ⚠️ «Накопительный счёт» (T_savings_out) и капитал.** → Перевод на сбережения вне приложения не трата, поэтому деньги не должны «исчезать» из капитала. Если у тебя заведён ручной счёт с флагом «принимает сбережения», переводы после даты его баланса прибавляются к нему. Если такого счёта нет — создаётся псевдосчёт «Сбережения вне MoneyManager (по переводам)» = Σ T_savings_out − Σ T_savings_in за всю историю, с предупреждением «это не баланс банка». Ликвидность псевдосчёта по умолчанию `instant`. → Иначе каждый перевод в копилку уменьшал бы капитал, а это противоречит §3.2. Оценка по переводам не видит процентов и снятий мимо категории, поэтому только как временная мера. → Заведи ручной счёт (депозит) с реальным остатком и включи «принимает сбережения»; ликвидность псевдосчёта меняется в настройках счетов (id `__savings_flow__`).

**D30. Инвариант «возврат долга — капитал не растёт».** → Проверяется на величине «нетто + дебиторка». Само «нетто» по формуле §3.3 при возврате долга растёт (деньги вернулись на карту), а дебиторка по §3.3 в нетто не входит. → Это единственное прочтение, при котором и формула §3.3, и инвариант §3.2 выполняются одновременно. → `netWithReceivables` в `computeCapital`; показывается справочно.

**D31. Медиана базовых расходов.** → Берутся N полных месяцев перед текущим (по умолчанию 6). Месяцы раньше первой операции в данных не участвуют, пустой месяц внутри данных считается нулём. Если месяцев меньше N — предупреждение. → Иначе при коротком учёте медиана занижалась бы нулями. → `baselineMonthly` в `engine/ledger.ts`, N = `settings.baselineMonths`.

**D32. Проценты по ручным депозитам в капитале.** → В текущий капитал не добавляются: берётся остаток, который ты ввёл. Начисление процентов будет только в симуляторе (этап 3). → Консервативно, и «начисленные проценты ≠ доступные деньги» (§6.2). → Обнови остаток ручного счёта, когда проценты придут.

**D33. Отрицательный баланс счёта** (например, кредитная карта) считается в ликвидности всегда, независимо от вида ликвидности счёта. → Долг по карте не «блокируется». → `sumAvailable` в `engine/ledger.ts`.

## Обзор и хранение

**D34. Следующий доход и резерв до него.** → Ближайшая дата по расписанию доходов **строго после сегодня** (доход, пришедший сегодня, уже в балансе или как раз распределяется). Резерв = платежи по обязательствам с датой в [сегодня; дата дохода] **включительно** — платёж в день зарплаты резервируется заранее. Без расписания горизонт 30 дней с явной пометкой. → Консервативно: лучше зарезервировать лишнее, чем получить кассовый разрыв в день зарплаты. → `nextIncomeDate` в `engine/overview.ts`; расписание в «Настройки → Доходы».

**D35. JSON-бэкап приложения.** → Включает всё состояние, в том числе последний импорт MoneyManager. Ключи сортируются — повторный экспорт байт-в-байт тот же. Бэкап из более новой версии и суммы-дроби отклоняются; недостающие настройки дополняются дефолтами. → §12: «только локально, с экспортом и импортом JSON-бэкапа». → `engine/state.ts`.

**D36. Повторный импорт MoneyManager** заменяет прошлый импорт целиком (MoneyManager — источник правды по операциям). Настройки, ручные счета, обязательства, цели не трогаются; новые счета получают настройки по умолчанию. → —

## Цели (реализация, сессия 2)

**D37. ⚠️ Уточнение инварианта 1 при отрицательном балансе.** → «Назначено больше, чем есть» поднимается, когда Σ назначенного на счёте > max(0, баланс). Нехватка = назначено − max(0, баланс). Если на счёте ничего не назначено, а баланс ушёл в минус (овердрафт), это не нарушение инварианта целей: снимать с целей нечего, а сам минус виден в балансе и ликвидности. → Property-тест нашёл этот случай (сид 21108361): буквальное «0 ≤ −5 367» ложно, но предупреждение без вариантов бессмысленно. **Условие в property-тесте уточнено так же — это единственное место, где я менял тест после первого прогона; проверь, согласен ли.** Нехватку тест теперь проверяет строже (одна формула вместо двух допустимых). → `overAssignment` в `engine/goals.ts`.

**D38. Снятие с цели — запись с минусом, а не удаление.** → Назначения — журнал: «назначить» пишет +X, «снять» −X, «перенести на другой счёт» — пара −X/+X. Так видно, откуда и когда пришли деньги, и любое состояние воспроизводимо. → —

**D39. Порядок целей в дереве.** → По важности (выше — раньше), затем по `id`. → Детерминизм (§2). → `goalTree`.

**D40. Цели «подтвердить» с суммой 0.** → Цель с пометкой `unconfirmed` может иметь `targetMin = 0` (пример из §4.3: суммы резерва, переезда и лечения не заданы). Обычная цель — только > 0. Стратегии распределения (этап 3) такие цели пропускают и пишут об этом в объяснении. → «Не придумывай финансовые данные». Это уточняет D28: «Финансовая база» создаётся с 1 000 000 ₸ — сумма прямо в её названии в инструкции. → —

## Этап 3: распределение и симулятор

**D41. ⚠️ Шаг 0: чем покрывается R1.** → Формула §5.1 буквально вычитает R1 из поступления целиком и одновременно уменьшает R2 на свободные деньги «сверх R1». Это значит, что свободные деньги на счетах уже считаются отложенными под R1 — и вычитать R1 из поступления ещё раз было бы двойным резервом. Поэтому: сначала R1 покрывают деньги целей с ролью «обязательство», затем свободные деньги на мгновенных счетах; их остаток покрывает R2; поступление закрывает только непокрытое. → Иначе при деньгах на карте система резервировала бы платёж дважды и занижала «Доступно». → `step0` в `engine/ladder.ts`. Если хочешь буквальную формулу — поставь «свободные деньги» = 0 (будет флаг в настройках).

**D42. Резерв = корневая цель с ролью safety.** → Подцель с ролью safety (например, «Буфер адаптации» внутри «Переезда») — это часть другой цели, а не резерв. В примере §4.3 «Буфер адаптации» теперь с ролью «смена жизни». → —

**D43. Поступление уже в балансе.** → По умолчанию считается, что ты импортировал бэкап после зачисления: тогда поступление вычитается из «свободных денег», чтобы не посчитать его дважды. Переключатель на экране «Новое поступление». → —

**D44. Дневная модель симулятора.** → Месячный расход делится на дни поровну в тиынах (остаток по 1 тиыну первым дням). Порядок дня: доходы → события → платежи → расходы → проценты → покрытие минуса из доступных вкладов → проверка разрыва. День «сегодня» не считается для доходов и расходов (они в балансе), а для платежей и событий — считается. Разрыв = наличные < 0 после попытки покрыть из доступных вкладов; эпизод — от первого до последнего дня в минусе. → Детерминированно и проверяемо вручную (см. сценарные тесты 4, 5, 9). → `engine/simulate.ts`.

**D45. Уровень 3 стратегии A: «70% в резерв».** → 70% остатка назначаются резерву (сверх комфортного уровня — это «подушка»), 30% — по весам. Если резерва нет, 70% остаются свободными. → Инструкция допускает «резерв или ликвидную подушку»; метка на резерве защищает деньги от случайного расхода. → `settings.strategy.cushionShareBp`.

**D46. Веса уровня 3** (`importance × urgency`) применяются только к не-резервным целям; потолок каждой цели — комфортная сумма (или минимум). Кто упёрся в потолок, получает потолок, остаток перераспределяется. Округление — в тиынах методом наибольших остатков, при равенстве по `id`. → —

**D47. Назначения в прогнозе.** → Капитал во всех стратегиях одинаков: стратегия меняет только метки на деньгах, а не сами деньги. Различаются даты целей, резерв и недофинансирование. В прогнозе положительный прирост каждого месяца назначается целям той же стратегией. Неблагоприятный сценарий сдвигает только тот доход вида «работа», который ещё не начался. → Так в сравнении стратегий нет «магии»: разница в капитале появилась бы только от реальных действий (досрочное погашение, вклад), и они моделируются как события «что если». → —

**D48.
