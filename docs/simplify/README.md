# Задача: сделать Capital OS понятным для всех

Это самодостаточный бриф для исполнителя (человека или ИИ), который не участвовал в прошлых обсуждениях. Прочитай целиком, затем `diagnosis.md`, `concepts.md`, `personas-and-tests.md`, `baseline.md`.

## 1. Суть задачи одной фразой

Человек, который ведёт учёт в MoneyManager, но не разбирается в финансах, открывает Capital OS, загружает бэкап и **сразу, без настройки и без объяснений** понимает, сколько можно тратить до следующего дохода, сколько отложить и успевает ли он к своим целям.

Сейчас это не так: приложение непонятно даже его автору. Замер: **42 разных понятия** на экранах, **30 статей** глоссария, **72 поля ввода**, форма цели из **11 полей**, а главное число на «Обзоре» отвечает не на тот вопрос (см. `diagnosis.md`, раздел 2.1).

## 2. Что это за проект

- Личное PWA для решений о деньгах. Учёт ведётся в MoneyManager (Android); Capital OS импортирует его бэкап `.mmbackup` и считает.
- TypeScript, всё на клиенте, **без runtime-зависимостей** (свои DEFLATE, ZIP, ридер SQLite). UI — vanilla TS с хелпером `h()`, без фреймворка.
- `engine/` — чистые функции, деньги в целых тиынах, около 300 тестов. `app/` — интерфейс (`main.ts`, `screens/*`, `blocks.ts`, `ui.ts`, `dom.ts`, `help-text.ts`, `styles.css`).
- Хранение: IndexedDB `capital-os` → store `kv` → ключ `state`; JSON-бэкап приложения — «Ещё → Бэкап».
- Решения и их причины — `docs/DECISIONS.md` (D1–D90). Блокеры среды — `docs/BLOCKERS.md`.
- Сайт: GitHub Pages, собирается при каждом push в `main`.

## 3. Что уже решено владельцем (не пересматривать)

- **Зависимость от MoneyManager принимается.** Аудитория — те, кто ведёт учёт в MoneyManager. Ручной режим и импорт выписок — не в этой задаче.
- **Встроенного ИИ-помощника не будет.** Понятность достигается устройством приложения, а не чатом поверх него.
- Существующий интерфейс (этапы 0–8, D76–D90) владелец считает «чрезмерно замудрённым», даже после переделки подписей. Косметика не решает задачу.
- Данные не покидают устройство; никаких серверов и внешних запросов во время работы.

## 4. Предлагаемое направление (нужно подтвердить у владельца перед кодом)

Подробно — `diagnosis.md`, раздел 4. Кратко:

1. **Два слоя.** Простой (по умолчанию, ≤ 12 понятий) и подробный («Подробнее», «Для продвинутых») — туда уходит всё нынешнее богатство: капитал, сценарии, стратегии, коэффициенты, свои типы.
2. **Главное число — «Можно тратить до [дата] — X ≈ Y в день»** вместо нынешнего «Свободно».
3. **Роль счёта:** кошелёк / копилка / не моё — одна вместо пяти настроек.
4. **Цели — очередь над копилками:** название, сумма, срок; важность — порядок; встроенная подушка; деньги распределяются автоматически; без ролей, подцелей, ручного «закрепить».
5. **Ритуал «Пришли деньги»:** один экран-совет «отложи X, на жизнь останется Y ≈ Z в день».
6. **Траты — 4 корзины,** поведение в прогнозе определяется по данным.
7. **«Планирую…»** — шаблоны событий вместо «Плановых событий», «Что если», «Альтернатив».
8. **Проверка смысла** — приложение само находит нестыковки (доход пропал, траты со всплесками и т. п.).

Ты можешь предложить другое решение, если оно лучше проходит тесты из `personas-and-tests.md`. Но обоснуй это замером и сценариями, а не вкусом.

## 5. Вопросы к владельцу — задать до кода

1. Согласен ли он, что главное число — «Можно тратить до даты», а капитал уходит во второй слой?
2. Роли счетов «кошелёк / копилка / не моё» — да?
3. Цели как очередь без ролей и подцелей; стратегии — только в подробном слое — да? Как переносить его нынешние подцели (слить в родителя или сделать отдельными целями)?
4. Размер встроенной подушки по умолчанию: 3 месяца обязательных трат и платежей по долгам — да?
5. Нужен ли казахский язык интерфейса для массовой аудитории (сейчас только русский)? Скорее всего — отдельная задача.

## 6. Ограничения (обязательные)

- **Push в `main` публикует сайт.** Работа — в отдельной ветке, PR в `main`; сливать только с согласия владельца. Один логичный коммит на шаг.
- **Математику движка не менять без явного согласия владельца.** Этот проект её меняет (роли счетов, «можно тратить», очередь целей) — поэтому сначала спецификация и «да», потом код. Если меняется ожидание теста — запись в `docs/DECISIONS.md` с объяснением (как D48).
- **Старые данные должны открываться.** Перенос состояния версии 1 → новая модель без потери денег, целей, рассрочек, истории решений. Перенос детерминирован и покрыт тестами.
- **Сначала защита данных.** В `app/store.ts` подтверждён дефект: если сохранённое состояние не прочиталось, приложение стартует пустым, и первая же запись затирает данные; ошибка записи не показывается. Перед любым переносом модели это нужно исправить (план — `claude/audit-2-verification.md` в проекте владельца; суть: не писать поверх нечитаемого состояния, сохранить исходник отдельно, показать ошибку записи).
- **Ничего «под одного человека»** (D72): никаких названий категорий, счетов, целей владельца в коде. Всё общее.
- Не добавлять runtime-зависимости и внешние запросы.
- Интерфейс по-русски, на «ты», короткими фразами.
- **Никогда не коммитить реальные бэкапы** и финансовые данные. Фикстуры — только синтетические (`scripts/make-fixtures.ts`).

## 7. Как запустить и измерить

```
bun test                                  # тесты движка (или npm test)
tsc --noEmit -p tsconfig.local.json       # типы engine + app
PORT=5199 bun scripts/dev-server.ts &     # сервер (или npm run dev)
bun scripts/complexity-audit.ts after     # замер сложности → ui-shots/complexity/after.json
bun scripts/ui-check.ts                   # доступность и мусор в тексте
bun scripts/ui-shots.ts <папка>           # снимки экранов
```

Адрес: `http://localhost:5199/?today=2026-10-28`. Состояния данных для снимков и замеров — `scripts/ui-states.ts` (`empty`, `imported`, `configured`, `broken`), фикстуры — `tests/fixtures/*.mmbackup`. Добавь состояния под персоны из `personas-and-tests.md` (минимум «студентка» и «семья»), если меняешь модель.

В облачной среде npm-реестр может быть закрыт — тогда только Bun (см. `docs/BLOCKERS.md`, B1).

## 8. Как вести работу

| Этап | Результат | Готово, когда |
|---|---|---|
| 0. Защита данных | Исправлен `app/store.ts` (см. 6) + тесты | Нечитаемое состояние не затирается; ошибка записи видна |
| 1. Спецификация | Документ `docs/simplify/spec.md`: экраны простого слоя (текст каждого экрана, поля, действия), расчёт «можно тратить», очередь целей, роли счетов, перенос данных, что уходит в подробный слой | Владелец сказал «да» |
| 2. Движок: счета и «можно тратить» | Роль счёта, новый расчёт, перенос, тесты инвариантов 1, 4 | Тесты зелёные, DECISIONS обновлён |
| 3. Движок: цели-очередь | Встроенная подушка, очередь, перенос целей и меток, тесты инвариантов 2–4 | То же |
| 4. Автоматика | Корзины трат, регулярность по данным, поиск доходов и «доход пропал», тест инварианта 5 | То же |
| 5. Интерфейс простого слоя | Главная, Копилки и цели, Пришли деньги, Планирую, Ещё; старое — под «Подробнее» | `ui-check` зелёный, снимки просмотрены |
| 6. Проверка смысла | Список правил с кнопкой «Исправить» | Каждое правило покрыто тестом |
| 7. Замер и тест на людях | `complexity-audit after` против `baseline.md`; протокол теста новичка (владелец находит 3–5 человек) | Пороги из `personas-and-tests.md` выполнены |

Каждый этап — отдельная ветка и PR. В PR: что сделано, замер до/после, снимки ключевых экранов, что не сделано и почему, вопросы владельцу.
